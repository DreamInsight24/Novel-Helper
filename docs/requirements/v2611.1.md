## 1. 背景与目标

v2610.3 完成了多小说首页、设定界面视觉化、AI 设定生成与桌面化，但在实际使用中暴露出四类问题：设定编辑体验仍然粗糙（新建入口、字段模板、分类与标签、信息层级）、关联（关系）功能不可用且缺少全局视角、缺少独立可视化的人物档案形态、以及没有移动端。v2611.1 的目标：

1. **修复与打磨设定编辑体验**：新建条目直接可用并带出模板字段，物品分类与标签真正可用，关键信息不再埋进「更多」，导入导出链路修复，AI 工作站可用性问题修复。
2. **把关联重构为「关系网」**：修复关联创建，新增全局关系网模块；设定内只保留以自身为中心、长度为 1 的放射图；重做创建关联界面；上下文拼装时让每个条目携带与自己相关的全部关联。
3. **新增角色卡**：独立、可视化程度高的 OC 档案，入口在首页作品库下方，面向「只想查看/创建角色、不写小说」的用户。
4. **移动端移植方案**：分析安卓与鸿蒙的可行性与具体方式，产出可评审的方案文档（本版本不实现、不出安装包）。

**非目标**：

- 不引入账号、云同步、多人协作或在线发布；
- 不改变现有多小说数据布局与集合字段语义（本文明确要求调整的除外）；
- 不重做桌面端整体视觉体系，只修复信息层级与交互；
- 不在本版本做世界地图、记忆的 AI 生成（沿用 v2610.3 结论）；
- 不实现用户自定义设定输入格式（纯文字、数据验证、枚举等），列为后续版本方向（见 4.1 要求 7）；
- 不实现安卓/鸿蒙应用与安装包，只产出《移动端移植方案》（见第 7 章）；
- 不提供 iOS 版本；
- 不要求角色卡与小说人物档案双向同步（本版本允许单向导入，见第 6 章）。

## 2. 任务总览

难度采用 1–5 级：1 极低、2 低、3 中、4 高、5 极高。难度按「实现 + 迁移/兼容 + 自测 + 文档」综合评估。

| 编号 | 任务 | 分支 | 难度 | 主要依赖 |
|---|---|---|---|---|
| 1 | 设定体验修复与小改动 | `dev/v2611.1-bugfix` | 高（4/5） | 无；其他任务的基础 |
| 2 | 关系网重构 | `dev/v2611.1-relation` | 高（4/5） | 任务 1 的设定页结构与「关联」入口 |
| 3 | 角色卡 | `dev/v2611.1-card` | 中（3/5） | 无；可与任务 2 并行 |
| 4 | 移动端移植方案（安卓 + 鸿蒙） | `dev/v2611.1-mobile` | 中（2/5） | 无；只读分析，产出方案文档 |

**执行顺序**：任务 1 → 任务 2 → 任务 3 / 任务 4（方案任务，可与任务 3 并行）→ 集成发布。任务 4 只产出方案，不进入实现与发布构建。

任务 1、任务 2 都会修改 `web/records.js`、`web/relations.js`、`web/style.css`，默认串行合并；任务 3 主要新增页面与全局数据模块，任务 4 只产出方案文档、不改实现代码。如确需并行，只能先做不合并的设计稿或独立文件，由负责人协调同一文件的改动。

## 3. 通用要求

### 3.1 分支、提交与 PR

- 开始前由负责人基于 `master` 创建 `dev/v2611.1`，再从该分支创建四个任务分支：`dev/v2611.1-bugfix`、`dev/v2611.1-relation`、`dev/v2611.1-card`、`dev/v2611.1-mobile`；
- 每个任务从对应分支拉出，PR 目标分支为 `dev/v2611.1`；
- 合并策略沿用仓库约定：squash merge；
- PR 必须包含变更说明、影响范围、自测清单、文档链接和 UI 截图/录屏；
- 任务 1 的设定编辑体验方案、任务 2 的关系网方案、任务 4 的技术选型需负责人 review 通过后才能合并；
- 不得在任务分支中顺带重构无关模块。

### 3.2 完成定义（DoD）

代码合并 + 文档更新 + 自动化测试/冒烟通过 + 必要的手工验收 + 打包验证（涉及资源、启动方式或移动端时）+ review 通过 + 验收标准逐条勾选。

### 3.3 国际化与文案

- 新增界面文案必须同时提供 `zh-CN` 与 `en-US`，key 集合一致，使用整句 key 与占位符；
- HTML 静态文案使用 `data-i18n`，JS 动态文案使用 `t()`；动态插入 DOM 后调用 `i18n.apply()`；
- AI 系统提示词、模型指令、日志和异常堆栈不进入翻译表，也不在界面展示；
- 用户数据（小说名、设定名、字段值、角色卡内容）不翻译；
- 删除文案时同步删除两个语言文件中的 key，并运行 `scripts/test_i18n.cjs`。

### 3.4 数据安全与兼容

- 首次启动初始化、新建小说、新建角色卡必须可重复执行且不覆盖已有数据；
- 不改变现有多小说布局：全局 `data/config.json`、小说数据 `data/novels/<novel_id>/`、工作区 `workspace/novels/<novel_id>/`；
- 新增数据必须可选字段，旧数据缺少时按默认值处理；
- 角色卡为全局数据，不得写入小说目录，不得随小说删除而丢失；
- 涉及数据的改动必须先备份、可重复执行、失败可回滚。

## 4. 任务 1：设定体验修复与小改动

**分支**：`dev/v2611.1-bugfix`

### 4.1 设定新建与编辑器重构

**现状**：新建走顶部弹窗，只能填名称、一句话概述与正文；创建后条目 `elements` 为空，人物要逐个「添加信息分组」；物品分类、标签、备注等关键信息位于「更多」；「正文」占据主视觉；分类只能手工添加基础信息。

**要求**：

1. **取消新建弹窗**：点击「新建」直接创建并选中新条目，名称使用默认名（如「新角色」「新物品」），可直接在编辑器中改名；不再有从顶部浮现的引导弹窗。
2. **创建时带出模板字段**：新建条目直接拥有该栏目元素模板的字段，人物至少包含姓名、身份、年龄等基础字段，用户可删除不需要的字段；不再需要逐个添加分组。模板字段来源与「元素模板 → 应用到全部」一致。
3. **物品分类**：在创建/编辑主界面提供分类选择，展示现有分类（默认枚举：道具、服装、其他）并提供「＋新建分类」；默认「道具」；分类变更即时保存。
4. **标签可用**：标签不再只出现在「更多」。主界面以 chip 形式支持添加、删除、筛选；补齐标签重命名与删除（跨条目生效，删除前确认）。
5. **信息层级**：分类、标签、备注等关键信息移回主界面；「更多」只保留结构编辑、搬运、删除、来源等低频操作；「正文」按 4.1.1 降级。
6. **风格化**：新建、编辑、分类与标签控件与设定页视觉一致，不再使用老旧输入框与三层嵌套布局。
7. **栏目独立性**：基础设定栏目（人物档案、人物背包、世界设定、地图设定、势力设定、物品）每个都是独立单元，功能独立、尽量减少耦合。改造不得把某个栏目的行为硬编码进其它栏目，也不得让基础栏目依赖扩展栏目。后续版本会支持用户自定义设定输入格式（纯文字、数据验证、枚举等），本版本不实现，但数据结构与编辑逻辑不得写死为「只能纯文字」。

**4.1.1 关于「正文」**：`content` 字段继续保留在数据格式、导入导出与 AI 拼装中，避免破坏既有数据。界面上把它降级为「其他」分组中的可选补充项（可命名「其他」/「补充描述」），用于补充卡片式字段难以描述清楚的部分；不再作为主编辑区，也不彻底移除。

### 4.2 新建小说的默认栏目

**现状**：新建小说会创建全部内置栏目（世界设定与 7 个扩展栏目），侧栏与设定管理显得拥挤。

**要求**：新建小说时只显示基础设定栏目（人物档案、人物背包、世界设定、地图设定、势力设定、物品）与「其他设定」；其余内置扩展栏目（物种、魔法与技能、地点与城市、历史与时间线、经济与物价、规则与疾病、宗教与信仰）默认隐藏，用户可在「设定管理」中开启。默认显示清单已确认按此执行。

**实现方向**：调整 `store/_defaults.py` 的 `default_sections()`，把扩展栏目的 `on` 置为 `false`；不删除栏目定义、不删除数据；`store/_layout.py` 的迁移逻辑保持既有小说行为不变。基础设定栏目各自独立，新增或隐藏某个栏目不得影响其它栏目的显示与数据。

### 4.3 分类管理与空状态

**要求**：

1. **分类管理**：支持重命名与删除（删除前二次确认，条目保留并回到「未分类」）；入口从左侧列表卡片移到页面头或设定管理区，位置与视觉统一，不再使用只能增加、不能删除的旧弹窗。
2. **空状态**：删除「没有匹配条目」中的 AI 生成设定按钮；无匹配时只显示空状态文案，并提示使用右上角「新建」。页头的 AI 设定生成入口保留。

### 4.4 导入导出链路排查

**要求**：对导入导出做一次完整排查，覆盖 `/api/import`、`/api/file`、`/api/io/save`、`/api/export`、`/api/io/export`、`project.import_sources()`、前端紧凑导入面板、AI 设定生成的文件读取链路、导出按钮与工作区路径解析。

**已确认缺陷**：`app/novelhelper/project/_imports.py` 的 `records_from_md()` 使用 `Path(source).stem`，但模块未导入 `pathlib.Path`。任何不含二级标题的 `.md`/`.txt` 导入会直接抛出 `NameError` 并返回 500，用户看到的是「导入失败」。

**已知问题**：

- 上述 md/txt 导入 500；
- AI 设定生成对话框读取导入目录 `.txt`/`.md` 的链路：`state.sources` 刷新时机、`/api/file` 路径解析、格式过滤、读取失败提示；
- 紧凑导入面板（`records.js` 的 `importPanel`）：本地文件选择、落盘路径、格式识别、导入源下拉刷新；
- 前端多处回退路径仍写作 `workspace/import`、`workspace/export`、`workspace/text`，与小说工作区 `workspace/novels/<novel_id>/...` 不一致；
- 导出默认覆盖同名文件，无提示或自动编号；
- 导入/导出目录变化后，前端缓存（`state.sources`、`state.io`）未刷新。

**要求**：

1. 修复 `records_from_md()` 缺陷，并为「有二级标题」「无二级标题」「空文件」「大小写扩展名」补充测试；
2. 路径解析统一走 `project.safe_rel()` / `store.io_in()`，禁止前端把绝对目录与文件名拼接后直接提交，禁止回退到旧的 `workspace/import` 全局路径；
3. 导入源列表在写入/删除文件后应可刷新；AI 设定生成对话框打开时应反映最新文件；
4. 修复后补充端到端测试（导入 → 列表 → 导出 → 再导入），并确认小说工作区隔离：A 小说的导入/导出文件不会出现在 B 小说。

### 4.5 AI 工作站

**要求**：

1. **模型选择**：输入区增加模型选择，选项来自当前接口的模型列表（与「模式管理」一致），默认「跟随当前模式」；选择结果随本次请求发送（后端 `/api/workstation/run` 已支持 `override.model`）。
2. **文案精简**：删除输入框下方过长的提醒文本（`workstation.context_hint`）；`workstation.prompt_help` 一并删除或缩为一句；保留模式、目标字数等必要控件。
3. **目标字数**：把含义不明的「硬性要求」改为「限定字数 / 不限字数」二选一。选择限定字数时填写目标字数并作为强约束发送；选择不限字数时不发送目标字数。后端保持 `target_chars` / `strict_length` 字段兼容，界面不再出现「硬性要求」字样。

### 4.6 验收标准

- [ ] 不含二级标题的 `.md`/`.txt` 导入成功，不再 500；含标题、空文件、大小写扩展名均有测试；
- [ ] AI 设定生成可从导入目录读取 `.txt`/`.md`，文件列表反映最新文件；
- [ ] 紧凑导入面板可本地选文件、落盘到当前小说导入目录并导入成功；
- [ ] 新建条目不再弹出引导弹窗，创建后直接选中并可改名；
- [ ] 新建人物直接带出模板字段（含姓名、身份、年龄等），可删除；
- [ ] 物品可在主界面选择/新建分类，标签可添加、删除、筛选、重命名；
- [ ] 分类、标签、备注在主界面可见，「更多」只余低频操作；
- [ ] 「正文」降级为「其他」补充项，字段与数据格式保留；
- [ ] 新建小说默认只显示核心设定栏目与「其他设定」，扩展栏目可在设定管理开启；
- [ ] 分类管理支持重命名与删除，入口位置统一；
- [ ] 空状态无 AI 生成按钮，提示右上角新建；
- [ ] 导入导出端到端测试通过，小说工作区隔离；
- [ ] AI 工作站可选择模型，长提醒文本已删除，目标字数为「限定/不限」；
- [ ] 中英文案齐全，1024×720 与 1440×900 截图通过；
- [ ] `docs/architecture.md`、`docs/api/server.md`、`docs/code-map.md`、`docs/localization/i18n-inventory.md`、README 与 `CHANGELOG.md` 已更新。

### 4.7 交付物

- 导入导出链路修复与测试；

## 5. 任务 2：关系网重构

**分支**：`dev/v2611.1-relation`

### 5.1 修复关联创建

**现状**：关联图设计有误，无法创建关联条目，问题较大。可能原因包括：前端创建关联对话框的保存链路异常、关联选择器无法直接新建目标条目（`records.create_linked` / `records.no_match_create` 两个文案已存在但功能未实现）、后端 `relations.normalize(data, db, strict=True)` 会因一条坏关联拒绝整批保存、防抖未落盘时校验失败等。

**要求**：

1. 先复现并定位根因，修复后补充回归测试；
2. 任何一条坏关联（悬空指针、自环、空关系名）不得阻塞其它关联的保存；坏关联应被丢弃并给出可读提示；
3. 关联选择器支持直接「新建并关联」：在无匹配条目时可新建目标条目并立即建立关联，新条目套用栏目模板；
4. 关联保存后，关系图与直接关联列表立即更新，防抖保存不丢数据。

### 5.2 关系网模块

**要求**：

1. 新增全局「关系网」页面（小说内），可查看本小说全部条目与全部关联，即全部关系网络；
2. 支持按栏目筛选、搜索、缩放/平移、重置视图；
3. 支持在关系网中创建、编辑、解除关联（复用 5.5 重做后的界面）；
4. 关联数据仍以 `relations` 集合为准；势力成员等条目关系继续作为投影双向同步；
5. 关系网不改变现有关联数据格式与集合字段语义。

### 5.3 设定内的关系视图

**要求**：

1. 设定条目的「关联」页只显示以该条目为中心、长度为 1 的放射图（自己 + 直接关联条目），不提供展开与多级钻取；
2. 直接关联列表保留：方向、关系类型、对端条目、备注、编辑与解除；
3. 需要查看全局关系时，引导用户前往「关系网」。

### 5.4 双击跳转

**要求**：在任意关联图（关系网、设定内放射图）中双击另一个条目，迅速跳转到该条目对应的设定页，并直接定位到其「关联」页。记忆、世界地图等没有条目编辑页的节点，保持现有降级行为（弹窗查看）或跳转到对应页面，但不得出现无反应或错误跳转。

### 5.5 创建关联界面重做

**要求**：

1. 重做比例与控件：搜索、栏目筛选、关系名称（预设建议 + 自定义）、方向（当前 → 对方 / 对方 → 当前 / 双向）、备注；
2. 输入框、下拉、按钮与弹窗尺寸协调，不再出现比例失调和老旧控件；
3. 支持 5.1 的「新建并关联」；
4. 键盘可用（Tab 焦点可见、Enter 选择、Esc 关闭），无匹配时有明确空状态与新建入口；
5. 编辑既有关联时保留方向、类型与备注。

### 5.6 拼装时携带关联

**要求**：

1. 上下文拼装时，关联合并到每个条目的渲染块中：每个条目列出与自己相关的全部关联（对端名称、方向、关系类型、备注）；
2. 不再单独输出全局「条目关联」区块；

## 6. 任务 3：角色卡

**分支**：`dev/v2611.1-card`

### 6.1 定位

- 角色卡是人物档案的扩展，或者更准确地说，是一个独立的人物档案功能；
- 目的是让用户更便利地查看和创造自己的 OC，即使用户并不打算真的去生成一本小说；
- 角色卡是相对独立、可视化程度较高的界面，与小说的人物档案不完全一致；
- 本版本不包含关联图。

### 6.2 入口与布局

1. 入口位于首页「作品库」下方，新增「角色卡」区块与「添加角色卡」按钮；角色卡是全局功能，不依赖当前活动小说；
2. 卡片为纵向长方形，上半 3/5 为人物图像（无图时使用默认图像），下半 2/5 显示角色基本信息：姓名、性别、身份；
3. 点击卡片后，右侧显示该角色的详细信息；
4. 支持新建、编辑、删除（二次确认）、搜索与排序；
5. 卡片网格 + 右侧详情的主从布局，与首页共用颜色、间距、圆角和按钮规范。

### 6.3 数据模型

1. 角色卡为全局数据，跨小说存在，建议 `data/cards.json`（或独立全局集合），不得写入小说目录；
2. 字段：`id`、`name`（姓名）、`gender`（性别）、`role`（身份）、`age`（年龄）、`tags`（标签）、`summary`（简介）、`notes`（备注）、`image`（图片引用）、`created`、`updated`；
3. 图片保存到全局资源目录（如 `data/card_images/`），JSON 只保存引用；提供内置默认图片；
4. 删除小说不得删除角色卡；首次启动初始化空的角色卡数据。

### 6.4 交互与视觉

- 卡片正面信息层级清楚：图片、姓名、性别、身份；
- 详情面板展示全部字段与标签，支持编辑与删除；
- 键盘可用：Tab 焦点可见、Enter 打开、Esc 关闭详情；删除确认默认焦点在取消；
- 1024×720 与 1440×900 下无横向滚动，中英文案齐全；
- 空状态有引导文案与新建入口。

### 6.5 与小说人物档案的关系

- 角色卡独立存储，不参与小说 AI 上下文拼装；
- 可选：从小说人物档案导入/复制为角色卡（本版本可不实现，作为后续增量）；
- 不得让角色卡与小说人物档案互相覆盖或产生隐式同步。

### 6.6 验收标准

- [ ] 首页作品库下方有「角色卡」入口与「添加角色卡」按钮；
- [ ] 卡片为纵向长方形，上 3/5 图为图像（无图用默认图），下 2/5 显示姓名、性别、身份；
- [ ] 点击卡片右侧显示详细信息，可编辑、删除（二次确认）、搜索、排序；
- [ ] 角色卡为全局数据，切换/删除小说不影响；
- [ ] 图片上传后正确保存并显示，缺失时显示默认图；
- [ ] 中英文案齐全，1024×720 与 1440×900 截图通过；
- [ ] 自动化测试与文档、CHANGELOG 更新。

### 6.7 交付物

## 7. 任务 4：移动端移植方案（安卓 + 鸿蒙）

**分支**：`dev/v2611.1-mobile`

**任务性质**：本版本只做方案，不写实现代码、不出安装包。交付物为一份可评审的《移动端移植方案》，供后续版本决定是否实施与如何实施。

### 7.1 目标

- 分析安卓（Android）与鸿蒙（HarmonyOS）两条技术路线的**可行性**与**具体方式**，给出推荐与理由；
- 给出现有代码到移动端的模块映射、数据与文件路径方案、网络与权限要求、AI 接口调用方式、工作量与风险；
- 明确哪些功能属于「可直接复用」、哪些需要「适配/重写」、哪些建议放到后续版本；
- 本版本不实现、不构建 APK、不发布安装包。

### 7.2 安卓可行性分析

必须覆盖以下路径并给出对比（可维护性、工作量、体积、兼容性、风险）：

1. **方案 A（推荐）**：Android WebView 外壳 + 内置本地 HTTP 服务（Kotlin + NanoHTTPD 或等价实现）承载现有 `web/` 前端；后端按模块移植到 Kotlin（`store` / `project` / `server` 核心子集），数据目录改为应用私有目录。前端零重写，成本集中在后端移植与文件/网络适配。
2. **方案 B**：Capacitor / Cordova 承载前端，后端移植或使用 Chaquopy 运行 Python。评估体积、兼容性、维护成本与 Android 10+ 行为。
3. **方案 C**：Android 仅作客户端连接桌面端。明确不满足独立使用的场景，只作为补充。

同时说明：目标系统版本（建议 Android 10 / API 29 起）、64 位要求、本地回环与明文流量权限、存储与导出/导入路径。

### 7.3 鸿蒙可行性分析

必须分析以下路径，并明确 HarmonyOS 各版本差异（尤其 HarmonyOS NEXT 不再兼容 Android APK）：

1. **原生 ArkTS / ArkUI 重写**：用 ArkTS 重做前端与后端，工作量大，但体验与系统集成最好；评估是否有必要；
2. **ArkTS + 本地服务 + WebView**：用鸿蒙 WebView 组件承载现有 `web/` 前端，本地 HTTP 服务与后端用 ArkTS/C++ 实现；评估鸿蒙对本地回环服务、文件访问的支持；
3. **跨端框架（Flutter / React Native 等）**：评估用一套跨端代码同时覆盖安卓与鸿蒙，或对现有前端改造的可行性；
4. **HarmonyOS 兼容模式**（仅适用于非 NEXT 版本）：说明其限制，不作为长期方案。

同时说明：目标设备与系统版本、鸿蒙应用形态、分布式能力是否利用、与安卓端数据互通方式（导出/导入）。

### 7.4 方案对比与推荐

- 给出安卓与鸿蒙的推荐路径，以及「先做哪个、后做哪个」的顺序；
- 若资源有限，明确建议的 MVP 范围（建议：多小说、设定、AI 工作站、稿件处理；关系网、角色卡视成本后置）；
- 对比表格至少包含：技术栈、前端复用度、后端移植量、包体积、维护成本、风险、预计工作量（人日）。

### 7.5 数据、签名与发布策略

- 数据本地优先，保存在应用私有目录；支持导出/备份（JSON 或 ZIP）与导入；不引入云同步；
- 多小说隔离规则与桌面端一致；
- 发布方式：开源 + GitHub Releases 分发，只出**签名 APK + SHA-256 校验文件**，不做 AAB（AAB 仅对应用商店上架有意义）；密钥不入库，由 CI 或本地注入；
- `versionCode` / `versionName` 与 `novelhelper._version.APP_VERSION` 对齐。

| 移动端实施阶段适配导致桌面端回归（本版本未实施） | 实施时移动端样式只在断点内生效；桌面端截图回归 |
